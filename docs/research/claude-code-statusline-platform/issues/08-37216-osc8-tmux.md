# Do OSC 8 hyperlinks from statusline scripts work inside tmux?

**Scope:** Status of `#37216` (re-report of `#23438`) and whether statusline clickable links survive Claude Code's rendering layer.
**Last updated:** 2026-04-18
**Confidence:** High — deep root-cause analysis in the issue, independent repro in related `#45173` (closed duplicate), Ink internals referenced.

## Answer

**Broken in tmux, broken in a subset of terminals outside tmux — and the root cause is inside Claude Code, not tmux.** OSC 8 hyperlinks written by statusline scripts are stripped because Claude Code writes the statusline outside Ink's React tree; Ink's render cycle calls `eraseLines()` and re-writes the region, destroying OSC 8 escape sequences that flowed through stdout. The text survives, the clickable link does not. Issue `#37216` is **open** on 2.1.73 with a precise rendering-pipeline walkthrough and a suggested fix (route statusline through Ink's `<Text>`/`<Link>`). Related `#45173` closed as duplicate 2026-04-15 after systematic repro. **Verdict: do not rely on OSC 8 from the statusline.** 2.1.113 added "Long URLs in responses and bash output stay clickable when they wrap across lines (in terminals with OSC 8 hyperlinks)" — explicitly a *response*/Bash-output fix, NOT a statusline fix.

## Evidence

- Issue: [`#37216`](https://github.com/anthropics/claude-code/issues/37216), state: open, opened 2026-03-21, updated 2026-04-08, 2 comments, labels `bug / has repro / platform:macos / area:tui / area:statusline`, 2.1.73.
- Root cause (OP quote):
  > Claude Code renders its statusline output **outside** Ink's React component tree, writing directly to the terminal. Ink's rendering cycle erases and rewrites all managed terminal lines on every update. This destroys any OSC 8 hyperlinks that were written directly to stdout by external statusline programs.
- Rendering pipeline walkthrough (OP):
  1. External statusline program writes OSC 8 hyperlinks to stdout
  2. Ink's next render cycle calls `eraseLines()` to clear previous output
  3. Ink rewrites its grid-rendered content (which doesn't include the external hyperlinks)
  4. The hyperlink text appears but is no longer clickable — the OSC 8 sequences were erased
- OP verified with `xxd` that the statusline binary outputs correct OSC 8 sequences — they are simply erased by Ink's render cycle. OP also verified `printf '\e]8;;URL\e\\text\e]8;;\e\\\n'` in the same tmux pane IS clickable — so tmux is not the culprit.
- Related closed as duplicate: [`#45173`](https://github.com/anthropics/claude-code/issues/45173) — closed 2026-04-15, systematic repro matrix across terminal/tmux combinations, confirmed root cause.
- Related open: [`#43328`](https://github.com/anthropics/claude-code/issues/43328) "Hyperlinks don't show in WindowsTerminal running claude in WSL" — open; likely same root cause.
- Changelog 2.1.113 (2026-04-17 approx): "Long URLs in responses and bash output stay clickable when they wrap across lines (in terminals with OSC 8 hyperlinks)" — addresses wrapped-URL clickability for *response output*, not statusline output.
- Workaround shared in comments (yurukusa): render your status in a separate tmux pane with `watch`, update from a Notification hook. Keeps OSC 8 in a rendering context Ink can't clobber. Not a statusline replacement — it's sidecar.

### Documented vs inferred

- **Documented:** OSC 8 from statusline is stripped by Claude Code's render pipeline. Not tmux, not Ghostty, not iTerm2 — Claude Code's layer.
- **Inferred:** the 2.1.113 fix demonstrates Anthropic HAS the plumbing to preserve OSC 8 through wrapping. Whether they'll port that to the statusline rendering region isn't signaled by any roadmap. `#37216` sits open.

## Caveats / Negative Signal

- Docs still advertise OSC 8 as a supported statusline output: "Links: use OSC 8 escape sequences to make text clickable… Requires a terminal that supports hyperlinks like iTerm2, Kitty, or WezTerm. See the clickable links example." — this is misleading; the docs list example works in some environments (direct terminal, no tmux, no Ghostty) but is unreliable.
- Some iTerm2 + no-tmux combinations DO work — the bug is most visible in tmux/Ghostty/Ink-heavy render paths.
- A real fix requires routing statusline content through Ink, which is a non-trivial refactor (the OP suggests it, Anthropic hasn't responded).

## Impact on statusline ideas

- Any idea presenting a *clickable link* (PR URL, session URL, dashboard URL) — **unreliable**. Ship the URL as plain text; accept that clickability is environment-dependent.
- Workaround "sidecar tmux pane" works but breaks the "lean statusline" model — not applicable.
- If the target audience is largely iTerm2-no-tmux, OSC 8 may work in practice. But any ship-to-all policy should assume OSC 8 from statusline is broken.
